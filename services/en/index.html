01 / Agent-assisted development

Audit and adoption using your team's tasks

For teams already trying AI agents for development, or looking to understand which tasks to delegate and how to verify the results.

Initial pilot

Estimate: 2 working weeks

One team, one repository, and 2–3 agreed tasks: from reviewing the current process to reproducible results in pull requests.

What you receive
A map of your current process and constraints, a workflow for completing tasks with agents, and recommendations for further adoption. The repository includes the changes, a task template, verification rules, and a team guide.
Scope
We review the selected tasks and configure access, spending limits, and checks in your existing CI. The pilot covers one repository and an agreed toolset. Adoption by other teams and redesigning the whole platform are discussed as a separate phase.
What we need from you
Your repository and CI, sample tasks and previous PRs, existing tests, approved models and tools, and requirements for handling code and data. You nominate an engineer to own the pilot and take part in acceptance.
Acceptance criteria
  • The selected tasks pass the agreed functional checks, with changes submitted as pull requests.
  • A deliberately introduced, testable defect blocks acceptance.
  • Your engineer reproduces the process by following the guide.
  • The report records costs, limitations, and the basis for deciding on the next phase.

02 / Engineering automation

One process, from start to result

For recurring work such as release preparation, change validation, environment setup, or engineering data processing.

Initial pilot

Estimate: 1–2 working weeks

One process, with up to two integrations into existing systems. Initial execution and failure testing take place in a test environment.

What you receive
A working automated process with execution logs, error diagnostics, and a maintenance guide. For example: validate changes, build an artifact, and prepare it for release. Your team receives the source code and instructions for handling failures.
Scope
We automate one sequence of steps and the agreed exceptions, using your available APIs and infrastructure. Production rollout, system replacements, and ongoing support are estimated separately after pilot validation.
What we need from you
A description of the manual steps, typical examples and failures, test data, and access to the test environment and APIs. We also need rules for reruns, the expected result of each step, and a process owner who can confirm that the automation works correctly.
Acceptance criteria
  • Success and failure scenarios pass in the agreed test environment.
  • Reruns follow the documented rule, without unexpected duplicate actions.
  • The logs show where and why the process stopped.
  • You run and recover the process using the guide; before-and-after measurements are included in the report.

03 / B2B product

A working use case before full development

For a defined user need where you want to validate the architecture, integration, and main path to the result before full development.

Initial pilot

Estimate: 3–4 working weeks

One end-to-end user workflow and one key integration, from input data to a result delivered through an API or interface.

What you receive
A working implementation of the selected workflow, source code, a reproducible build, and tests. You also receive a record of architectural decisions, known limitations, and a plan for the next phase. This provides a basis for deciding on further investment in the product.
Scope
We implement one agreed sequence: accept a request, process it according to the rules, and return a result. We choose the stack needed for that sequence. A full feature set, all user roles, additional integrations, and production operation require a separate scope of work.
What we need from you
A description of the user and their task, a product owner available for timely decisions, sample data, integration contracts, and infrastructure constraints. We agree on workload volumes, response times, and access requirements before implementation, along with the verification scenarios.
Acceptance criteria
  • The end-to-end workflow works with the agreed data, including error handling.
  • Performance metrics are checked in the agreed test environment when included in the pilot.
  • You can build and run the solution by following the guide.
  • The demonstration, source code, and report let you verify the result and see the remaining limitations.

Before work starts

A pilot with clear boundaries

The timelines above are estimates for the stated scopes. After a short brief, we agree on deliverables, acceptance criteria, timeline, price, and spending limits for tools and infrastructure. Work starts once these are agreed and the required access is in place.

We also agree on permitted data and models, where the work runs, and who accepts the results. Scope changes are discussed before any additional work begins. The pilot ends with a demonstration, handover, and a decision on whether to continue.
